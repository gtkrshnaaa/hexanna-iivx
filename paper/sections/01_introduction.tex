\section{Introduction}
\label{sec:introduction}

Data engineering pipelines underpin modern analytics and operational machine learning, demanding continuous transformation, schema validation, multi-way relational joins, and format modernization. While distributed cloud data warehouses (e.g., Snowflake, BigQuery, AWS Redshift) dominate large-scale enterprise infrastructure, local data engineering workflows on commodity developer workstations remain vital. Developers and data scientists prioritize local processing due to corporate data sovereignty mandates, edge operational constraints, zero cloud egress expenses, and the need for rapid local iteration cycles.

Recent advancements in Large Language Models (LLMs) and autonomous agent frameworks \cite{yao2022react,schick2023toolformer} have stimulated interest in automating local data engineering tasks. Systems such as PandasAI \cite{mckinney2010pandas} and Open-Interpreter attempt to synthesize and execute data transformation code from natural language instructions. However, existing autonomous data engineering approaches suffer from fundamental architectural deficiencies when deployed on commodity developer hardware:
\begin{enumerate}
    \item \textbf{Context Window Saturation and Data Confidentiality Violations:} Naive agents ingest sample rows of raw tabular data directly into LLM prompts. On multi-gigabyte datasets, this approach rapidly exhausts finite context windows, inflates API token costs, and violates data governance mandates by transmitting raw proprietary records to third-party model inference endpoints.
    \item \textbf{Unbounded In-Memory Allocation and OOM Panics:} Systems delegating operations to in-memory DataFrame libraries (e.g., Pandas) require allocating contiguous matrices in RAM, scaling linearly with dataset cardinality $\mathcal{O}(N)$. On commodity workstations with 16~GB RAM, processing 10~GB datasets induces catastrophic memory spikes, triggering operating system kernel Out-of-Memory (OOM) killer terminations.
    \item \textbf{Arbitrary Shell Execution Vulnerabilities:} General-purpose agents executing arbitrary Bash commands present critical security vulnerabilities, including destructive filesystem modifications, path traversals, and non-deterministic side effects \cite{greshake2023not,liu2023jailbreaking,li2024evaluating}.
    \item \textbf{Lack of Out-of-Core Agent Orchestration:} While state-of-the-art columnar engines such as DuckDB \cite{raasveldt2019duckdb} and Polars \cite{polars2024} provide vectorized streaming capabilities, existing agent harnesses lack deterministic abstractions to orchestrate these engines under strict memory clamps and structured self-healing feedback loops.
\end{enumerate}

To resolve these challenges, we introduce \textbf{Hexanna IIVX}, a lightweight, deterministic agent harness designed specifically for out-of-core local data engineering. Hexanna IIVX decouples high-level cognitive reasoning from local hardware execution using a hexagonal architecture (ports and adapters). The agent interacts with underlying datasets exclusively through a metadata-first protocol: raw records are stripped locally, and only relational schemas and compact statistical profile sketches (cardinalities, quantiles, null proportions) are transmitted to remote OpenAI-compatible inference APIs. Execution is confined to a strictly-typed tool harness orchestrated over an embedded vectorized query engine (DuckDB) enforcing static memory limits and automatic NVMe disk spilling.

This paper addresses four fundamental Research Questions (RQs):
\begin{itemize}
    \item \textbf{RQ1 (Memory Bounds and Out-of-Core Invariance):} Can Hexanna IIVX maintain an invariant, predictable memory ceiling ($<550$~MB RSS) across multi-gigabyte workloads up to SF-10 (60 million records), completely eliminating the kernel OOM panics that plague in-memory agent frameworks?
    \item \textbf{RQ2 (Wall-Clock Latency and Orchestration Overhead):} What is the computational latency trade-off incurred by NVMe disk spilling during memory-constrained execution, and what is the exact marginal latency cost of LLM agent planning compared to zero-LLM manual execution?
    \item \textbf{RQ3 (Empirical Token Wire Invariance):} Does the metadata-first protocol empirically preserve an $\mathcal{O}(1)$ prompt token wire size as the underlying raw dataset expands tenfold from 1~GB to 10~GB?
    \item \textbf{RQ4 (Ablation and Self-Healing Convergence):} How significantly does the ProfileSketcher module improve first-shot query generation, and can the deterministic self-healing dispatch loop systematically recover from runtime execution errors without human intervention?
\end{itemize}

\noindent The primary scientific contributions of this work are summarized as follows:
\begin{itemize}
    \item \textbf{Metadata-First Agent Protocol:} We formulate and prove an $\mathcal{O}(1)$ token wire protocol that abstracts raw tabular records into compact schema profiles and statistical sketches, guaranteeing that remote model context windows never scale with dataset cardinality.
    \item \textbf{Sandboxed Out-of-Core Execution Harness:} We design a deterministic execution engine interface that eliminates arbitrary shell execution in favor of typed functional query tools, bounding peak memory consumption via configured buffer pool limits and automatic NVMe spilling.
    \item \textbf{Self-Healing Dispatch Loop:} We implement an automated diagnostic feedback loop that captures SQL syntax faults, type mismatches, and empty result sets, achieving a 100\% task completion rate across diverse analytical query profiles.
    \item \textbf{Rigorous Empirical Benchmarking:} We conduct an extensive empirical evaluation across TPC-H benchmarks (SF-1, SF-5, SF-10), benchmarking Hexanna IIVX against Raw DuckDB, Polars streaming, and in-memory Pandas agents across three distinct query profiles (aggregation, multi-way join, and correlated subqueries).
\end{itemize}
